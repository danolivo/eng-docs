# Логическая репликация: как подписчик согласует параметры сессии с публикатором

Документ описывает встроенную логическую репликацию PostgreSQL (`CREATE SUBSCRIPTION`, плагин `pgoutput`). Поведение проверено по исходникам ветки master:

- `src/backend/replication/libpqwalreceiver/libpqwalreceiver.c` — `libpqrcv_connect()`;
- `src/backend/replication/logical/proto.c` — `logicalrep_write_tuple()`, `logicalrep_read_tuple()`;
- `src/backend/replication/logical/worker.c` — `slot_store_data()`;
- `src/backend/libpq/pqformat.c` — `pq_sendcountedtext()`, `pq_sendtext()`;
- `src/backend/utils/mb/mbutils.c` — `pg_server_to_any()`.

В старых минорных версиях часть принудительных настроек может отсутствовать. Для конкретной версии это стоит проверить по её исходникам.

## 1. Как значение попадает с публикатора на подписчика

1. **Публикатор (walsender).** По умолчанию значение колонки переводится в текст output-функцией типа (`OidOutputFunctionCall`). Работает она с GUC сессии walsender'а. Затем текст уходит через `pq_sendcountedtext()`, которая **переводит его в кодировку клиента** (`client_encoding` этой сессии).
2. **Подписчик (apply worker).** Текст разбирается input-функцией **типа колонки на подписчике** с **typmod колонки на подписчике** (`OidInputFunctionCall`). Работает она с GUC сессии apply worker'а, то есть с настройками подписчика.

Значит, на результат влияют две независимые группы настроек: на выводе — настройки сессии walsender'а, на вводе — настройки подписчика. Подписчик управляет только первой. Свои GUC он намеренно не меняет. Цитата из `libpqrcv_connect()`: «We don't want to modify the subscriber's GUC settings, since that might surprise user-defined code running in the subscriber, such as triggers».

Начальная синхронизация таблицы (tablesync, `COPY ... TO STDOUT`) идёт через такое же логическое replication-соединение. Поэтому всё, что описано ниже, относится и к ней.

## 2. Что подписчик задаёт walsender'у при подключении

`libpqrcv_connect()` для логического соединения добавляет к строке подключения:

| Параметр | Значение | Зачем |
|---|---|---|
| `client_encoding` | кодировка базы подписчика | «Tell the publisher to translate to our encoding»: конвертирует публикатор |
| `datestyle` | `ISO` | однозначный вывод дат и времени |
| `intervalstyle` | `postgres` | однозначный вывод `interval` |
| `extra_float_digits` | `3` | точный (round-trip) вывод `float4`/`float8` |
| `search_path` | `''` (пустой) | сразу после подключения выполняется `ALWAYS_SECURE_SEARCH_PATH_SQL` |

Комментарий в коде: «Force assorted GUC parameters to settings that ensure that the publisher will output data values in a form that is unambiguous to the subscriber… This should match what pg_dump does».

Параметры `datestyle`, `intervalstyle`, `extra_float_digits` передаются через `options` (`-c ...`) и добавляются **после** того, что пользователь указал в `options` в строке подключения подписки. При одинаковом `-c` побеждает последний, поэтому пользователь не может переопределить эти три параметра. Остальные GUC публикатора через `options` задать можно.

## 3. Кодировка

Подписчик всегда просит публикатора перевести данные в свою кодировку. Что происходит дальше, решает `pg_server_to_any()` на публикаторе:

| Публикатор | Подписчик | Что происходит |
|---|---|---|
| X | X (та же) | Конвертации нет, байты передаются как есть, без проверки. |
| UTF8 | LATIN1 и т.п. | Публикатор конвертирует. Если символ непредставим в кодировке подписчика (кириллица в LATIN1, эмодзи), walsender завершается с ошибкой `character with byte sequence ... in encoding "UTF8" has no equivalent in encoding "LATIN1"`. |
| LATIN1 и т.п. | UTF8 | Публикатор конвертирует, из однобайтовой кодировки в UTF8 это всегда возможно. |
| `SQL_ASCII` | X ≠ `SQL_ASCII` | Конвертации нет (исходная кодировка неизвестна), но байты **проверяются** на корректность в кодировке подписчика. ASCII и корректные для X байты проходят, остальные дают ошибку `invalid byte sequence for encoding ...`. |
| любая | `SQL_ASCII` | Конвертации и проверки нет, байты сохраняются как есть. |

Что означает ошибка конвертации на практике:

- walsender падает, apply worker переподключается и снова получает ту же ошибку на той же транзакции. Репликация стоит, слот удерживает WAL, на публикаторе растёт занятое место;
- сама ситуация не разрешится. Нужно вмешательство: исправить данные на публикаторе или пропустить транзакцию (`ALTER SUBSCRIPTION ... SKIP (lsn = ...)`).

Тихой порчи из-за кодировки нет. Есть одно исключение: подписчик в `SQL_ASCII` принимает любые байты.

В binary-режиме текстовые типы передаются через `textsend()` → `pq_sendtext()`, и там та же конвертация. Поведение одинаковое.

## 4. Параметры сессии: что будет при расхождении

### Задаются принудительно — расхождение не влияет

- **`DateStyle`.** Публикатор всегда выводит ISO. ISO-ввод разбирается одинаково при любом `DateStyle` подписчика, включая порядок `DMY`/`MDY`.
- **`IntervalStyle`.** Публикатор всегда выводит в стиле `postgres`. Ввод в этом формате понимается при любом `IntervalStyle` подписчика.
- **`extra_float_digits`.** Публикатор всегда выводит точное значение, потерь нет.
- **`search_path`.** Публикатор работает с пустым `search_path`, поэтому reg*-значения (`regclass`, `regtype`, `regproc` и т.д.) выводятся со схемой (кроме объектов `pg_catalog`). Подписчик разбирает квалифицированное имя одинаково при любом своём `search_path`. Сохраняется имя, а не OID, поэтому на подписчике значение указывает на его собственный объект с тем же именем. Если такого объекта нет, будет ошибка.

### Не задаются, но расхождение безопасно

- **`TimeZone`.** `timestamptz` выводится со смещением (`2026-10-06 15:00:00+03`). Подписчик учитывает смещение и сохраняет тот же момент времени. Текст на узлах разный, значение одинаковое. На `timestamp`, `date`, `timetz` `TimeZone` не влияет.
- **`bytea_output`.** Ввод `bytea` понимает и `hex`, и `escape`.
- **`lc_numeric`, `lc_time`.** Влияют только на `to_char`, а не на output/input-функции.
- **`standard_conforming_strings`.** Значения передаются отдельно от SQL, литералы не разбираются.

### Не задаются, и расхождение опасно

- **`lc_monetary`.** `money` выводится по локали walsender'а (символ валюты, разделители, число знаков после запятой), а разбирается по локали подписчика. Последствия:
  - разные символы или разделители — ошибка разбора, репликация стоит;
  - разное число знаков после запятой — **тихое искажение**: значение сохраняется в другом масштабе.

  Что делать: одинаковый `lc_monetary` на обоих узлах, или binary-режим (`cash_send` передаёт целое без локали), или не использовать `money`. Задать `lc_monetary` публикатору можно через `options` в строке подключения подписки, но он должен совпадать с `lc_monetary` подписчика.
- **`xmloption`.** Вывод `xml` от него не зависит, а ввод на подписчике зависит. Если на подписчике `xmloption = document`, фрагмент XML (не целый документ) вызовет ошибку и остановит репликацию.

## 5. Различия узлов, которые не являются параметрами сессии

- **Типы колонок.** Колонки сопоставляются по имени, значение разбирается input-функцией типа подписчика. Поэтому разные типы допустимы, если текст разбирается (`int4 → int8`, `numeric → text`). Разбор не прошёл — ошибка и остановка.
- **typmod колонок.** Применяется typmod подписчика. `varchar(5)` при длинной строке даёт ошибку. `numeric(10,2)` и `timestamp(0)` **тихо округляют** значение.
- **Метки enum.** Передаётся текст метки. Если на подписчике такой метки нет, будет ошибка.
- **Версии расширений.** Input-функция типа на подписчике должна понимать вывод версии на публикаторе. Если формат изменился, будет ошибка или неверный разбор.
- **Major-версии.** Репликация между версиями поддерживается в обе стороны, версия протокола согласуется при старте (`proto_version`). Текстовый вывод разных версий разбирается input-функциями.
- **Collation и её версия.** В протоколе collation не передаётся. Apply worker ищет строку для UPDATE/DELETE по индексу подписчика с правилами сравнения подписчика. Если версия glibc или ICU сменилась без `REINDEX`, индекс фактически повреждён, и строка может не найтись. Тогда UPDATE/DELETE **молча пропускается**: до PG18 сообщение пишется на уровне `DEBUG1`, в PG18 это конфликт `update_missing` / `delete_missing` на уровне `LOG`. В результате данные на узлах расходятся.
- **Binary-режим** (`WITH (binary = true)`). Используются send/recv-функции, GUC сессии на них не влияют. Но тип на подписчике должен принимать бинарный формат типа публикатора. Разные типы (`int4` → `int8`) или разные версии типа дадут ошибку `incorrect binary data format`, неявного приведения нет.

## 6. Итог: что нужно согласовать вручную

Подписчик сам решает вопросы `DateStyle`, `IntervalStyle`, `extra_float_digits`, `search_path` и кодировки. Остальное — задача администратора:

1. **Кодировка:** кодировка подписчика должна уметь представить все символы публикатора. Иначе репликация остановится.
2. **`lc_monetary`:** одинаковый на обоих узлах, или binary-режим, или без `money`.
3. **`xmloption`:** на подписчике — `content` (значение по умолчанию).
4. **Типы и typmod колонок:** одинаковые, иначе возможны ошибки или тихое округление.
5. **Collation:** одинаковые версии библиотек или `REINDEX` после обновления glibc/ICU, иначе UPDATE/DELETE могут пропускаться.
6. **Метки enum и версии расширений:** одинаковые.
