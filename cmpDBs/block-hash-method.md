# ROW HASH, VERSION 6

0. Правило равенства и границы
   0.1 Значения идентичны ⇔ v::text совпадает при фиксированных настройках сессии.
       Каст в text задаёт автор типа; если каста нет, работает функция вывода.
       Ключи и строки подчиняются одному правилу.
   0.2 ACE не опирается на OID функций, типов, операторов и любых других
       объектов. SQL строится по именам. OID, прочитанный из каталога,
       используется только в той же сессии того же узла: он не сравнивается
       между узлами и нигде не хранится.
   0.3 Колонки типов oid и reg* (regclass, regtype, regproc, regprocedure,
       regoper, regoperator, regnamespace, regrole, regcollation, regconfig,
       regdictionary) не рассматриваются.

1. Подготовка: один раз на прогон / на дерево, на клиенте
   1.1 Колонки: все колонки таблицы, упорядоченные по имени (#248); i = 1..n.
   1.2 N_i = splitmix64(i): 64-битный маркер NULL, в SQL подставляется литералом.
   1.3 Кодировка каждого узла E_k берётся из ParameterStatus server_encoding.
   1.4 Опорная кодировка B:
         - все узлы SQL_ASCII                                → B = SQL_ASCII
         - все узлы не SQL_ASCII имеют одну кодировку E      → B = E
         - иначе                                             → B = UTF8
   1.5 Форма хэша значения на узле k, enc(v):
         E_k = B или E_k = SQL_ASCII                         быстрая
           hashtextextended(v::text COLLATE "C", i)
         иначе (тогда B = UTF8), любая версия PG 15+         медленная + WARNING
           CASE WHEN v IS NOT NULL
                THEN hash_record_extended(ROW(convert_to(v::text,'UTF8')), i) END
       Значение на всех узлах одно: hash_any_extended по байтам v::text
       в кодировке B (для SQL_ASCII — сырые байты).
   1.6 WARNING один раз на узел за прогон:
       "node n2: server_encoding is EUC_JP, not UTF8. Values are converted
        to UTF8 before hashing, so hashing on this node is slower."

2. Строка, на сервере
   2.1 h_i      = COALESCE(enc(c_i), N_i)
   2.2 row_hash = hashint8extended(h_1 # h_2 # … # h_n, 6)

3. Блок, на сервере
   3.1 (count(*), bit_xor(row_hash))   — после #209
       (count(*), sum(row_hash))       — до #209
   3.2 table-diff сравнивает пару на клиенте.
   3.3 Лист mtree хранит те же 16 байт; родитель — XOR детей.

4. Блок с расхождением (keydiff)
   4.1 Запрос ключей: k_j::text по каждой колонке ключа + row_hash.
   4.2 Карта на клиенте по кортежу k::text, сравнение row_hash.
   4.3 Чтение строки и проверки repair:
         k = $n::T AND k::text COLLATE "C" = ($n::T)::text
       Здесь T — имя типа колонки, не OID.
   4.4 Значения для отчёта и для записи в repair берутся как вывод
       (текстовый формат результата).

5. Что хранится
   5.1 mtree: версия хэша (6) + B. Если B по текущим узлам не совпадает
       с сохранённой, листья пересчитываются.
   5.2 Манифест diff: версия хэша + B. Repair (#210) пересчитывает row_hash
       с той же B.

КОНТРАКТЫ
 K1  Равенство = совпадение v::text.
 K2  (input(k::text))::text = k::text. Нарушение → ошибка поиска ключа,
     операция идёт в лог отказов repair.
 K3  a::text = b::text ⇒ a = b. Нарушение → строка не находится,
     в отчёте она как отсутствующая.
 K4  Настройки вывода зафиксированы на каждом соединении (outputSettings).
 K5  Хэш строится по байтам v::text в кодировке B. Узел в другой кодировке
     работает на любой версии PG 15+, но медленнее (WARNING).
 K6  Колонки сопоставляются по имени (#248).
 K7  bit_xor только при одном ключе на relation в блоке (#209), иначе sum.
 K8  Вероятность пропуска: 2^-64 на сравнение строки и на сравнение блока.
 K9  Порядок байт не учитываем.
 K10 Одна версия хэша и одна B на всех узлах и в mtree.
 K11 Никаких OID объектов между узлами (0.2); колонки oid и reg*
     не рассматриваются (0.3).
