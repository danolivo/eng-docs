# pgcmp — сравнение одной таблицы на двух инстансах PostgreSQL

Макет «прямолинейного» подхода из документа *Table Comparison — Do we need
technology?*: никаких хэшей и блоков, просто два потока строк в порядке
первичного ключа и слияние на клиенте. Сериализация целиком на сервере:
строка сравнивается как текст `ROW(c1, c2, …)` — ровно то, что показывает
psql для составного значения.

## Сборка

```sh
go mod tidy
go build
go test
```

## Запуск

```sh
./pgcmp -dsn1 'host=n1 dbname=db user=u' \
        -dsn2 'host=n2 dbname=db user=u' \
        -table public.orders \
        [-columns id,amount,status] \
        [-filter "status <> 'archived'"] \
        [-out orders.diff]
```

* `-dsn1` — опорная (reference) сторона, `-dsn2` — тестируемая.
* `-table` — имя, при необходимости со схемой. Без схемы — резолвится по
  `search_path` сессии на каждой стороне, так что таблица может жить в
  разных схемах.
* `-columns` — какие колонки сравнивать; по умолчанию все колонки опорной
  таблицы. Первичный ключ сравнивать не нужно, из списка он выбрасывается.
* `-filter` — выражение `WHERE`, подставляется как есть на обе стороны.
  Пока оно выполняется, `search_path = pg_catalog, <схема таблицы>`.

## Что делает

1. Подключается к обеим сторонам, выставляет одинаковые настройки сессии:
   `TimeZone`, `DateStyle`, `IntervalStyle`, `bytea_output`,
   `extra_float_digits`, `quote_all_identifiers`, `client_encoding`.
   Открывает `REPEATABLE READ READ ONLY` транзакцию — каталог и данные
   читаются из одного снапшота, а его потом можно экспортировать для
   параллельных воркеров.
2. Согласует структуру: с каждой стороны берёт колонки с `format_type`
   и первичный ключ. Требования первой версии:
   * PK есть, одноколоночный, типа `int2`/`int4`/`int8`, одного имени
     и с одинаковой collation с обеих сторон;
   * каждая сравниваемая колонка есть на обеих сторонах и имеет
     одинаковый `format_type` (тип + typmod).
   Любое расхождение — ошибка, «наиболее общий тип» не ищем.
3. На обе стороны уходит один и тот же запрос:
   `SELECT "pk", ROW("c1", "c2", …)::text FROM … [WHERE (…)] ORDER BY "pk"`.
   Строки вычитываются потоково в двух горутинах и сливаются.
4. Отчёт пишется в `-out`. Либо одна строка `match`, либо по строке на
   каждое расхождение:

   ```
   <pk> <строка опорной таблицы> <строка тестируемой>
   ```

   Отсутствующая строка обозначается `NULL`. Разделитель — пробел:
   `record_out` берёт в кавычки любое поле с пробельным символом, поэтому
   голого пробела внутри строки не бывает, а сама строка всегда начинается
   с `(` и не путается с `NULL`.

Коды возврата: `0` — совпали, `1` — есть расхождения, `2` — ошибка.

## Чего нет (пока)

* Параллелизм по диапазонам ключа (гистограмма + `pg_export_snapshot`).
* Составные и нецелочисленные ключи.
* Приведение к общему типу (`timestamp` ↔ `timestamptz` и т. п.).
* Экранирование перевода строки внутри значения: `record_out` берёт его
  в кавычки, но не экранирует, и строка отчёта разрывается на две.
